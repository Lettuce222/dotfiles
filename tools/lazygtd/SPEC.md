# lazygtd の仕様

lazygtd に求められていることを、これまでの話し合いから集めた。いま作れているかどうかは [HANDOFF.md](HANDOFF.md) の「いまできていること」「いまできていないこと」にある。ここには、目指す形を書く。

仕様の強さは、次の 3 つで書き分ける。

- 決まり: もう決めたこと。変えるなら、ユーザーと話してからにする。
- 向き: 方向は決まっているが、細かいところは作りながら決めてよいこと。
- 未定: まだ決めていないこと。作る前にユーザーに聞く。

## 1. 目的

- GTD の項目を、ターミナルの 1 画面で見て、片付ける。inbox を振り分ける、移す、完了にする、本文を読む、を速く行える。
- 人とエージェントが同じ項目を扱う。エージェントへの頼みごとも、エージェントからの答えも、lazygtd の中で読み書きする。
- 操作感と見た目は lazygit に寄せる。ユーザーは lazygit をよく使うので、迷ったら lazygit のとおりにする（向き）。
- ゆくゆくは、エージェントの窓口のターミナルを開かずに、lazygtd だけで頼みごとから答えまで済ませる（向き）。

## 2. 前提と、やらないこと

- 項目の形と操作の正は `gtd.py` にある。lazygtd は `gtd.py` の画面の 1 つで、データを独自に持たない（決まり）。
- GTD のうち、次のものは持たない（決まり）。
  - コンテキスト（@電話、@PC など）
  - 週次レビューの仕組み
  - カレンダー。日時の決まった予定は、「カレンダーに入れる」という次の行動として扱う
- 外のチケットや課題の管理（課題管理のサービスなど）は、項目からリンクするだけにする。中身を写さない（決まり）。
- 項目の中身に、情報の扱いの区分（機密の度合いなど）の欄は持たない（決まり）。
- 外のエディタやプラグインを同梱しない（決まり）。Markdown の表示などのライブラリは使ってよい。

## 3. 言葉

| 言葉 | 意味 |
| --- | --- |
| 項目 | GTD の 1 件。1 項目 1 ファイル |
| リスト | 項目が今いる所。`list` の値で持つ |
| プロジェクト | 複数の行動で達成するもの。ステップ（行動の id の並び）を持つ |
| ステップ | プロジェクトに並んだ行動。並びの順に進める |
| actor | その項目を進めるのは誰か。`me`（ユーザー）か `agent`（エージェント） |
| 窓口 | ユーザーの頼みごとを受けるエージェント（orchestrator）。項目を整理し、worker を起こし、承認を聞く |
| worker | 窓口が起こす、1 つの項目を進めるエージェント |
| あなたの番 | ユーザーが今動くべき項目の集まり |
| 返事 | 窓口の返事と、それへのユーザーの返事。項目の本文に積む |

## 4. データ

### 4.1 置き場所

- 項目: `${GTD_HOME}/items/<id>.md`。`GTD_HOME` が無ければ `gtd.py` の既定に従う（決まり）。
- 成果物: `${GTD_HOME}/items/<id>/` の下に置く（決まり）。
- 変更の記録: `${GTD_HOME}/.log/changes.jsonl`。どの書き込みも 1 行ずつ足される（決まり）。
- `GTD_HOME` はローカルの git にする。リモートは持たない（決まり）。

### 4.2 項目の形

frontmatter 付きの Markdown にする。主な欄は次のとおり。

| 欄 | 意味 |
| --- | --- |
| `id` | 作った時刻と短い乱数（例: `20261120-a3f2`）。変えない |
| `title` | 題 |
| `list` | `inbox`・`next`・`planned`・`project`・`waiting`・`someday`・`reference`・`done` |
| `project` | 属するプロジェクトの id |
| `actor` | `me` か `agent` |
| `worker` | 結ばれた worker の名前 |
| `due` | 締め切り（日付） |
| `since` | その状態になった日 |
| `links` | 関係する URL の並び |
| `outcome`・`short`・`steps` | プロジェクトだけが持つ。目指す結果、略称、ステップの id の並び |
| `who`・`follow_up`・`then`・`watch` | 連絡待ちだけが持つ。誰を待つか、いつ確かめるか、届いたら何をするか、状態を追う URL |
| `asked`・`answered`・`read` | 返事の時刻。ユーザーが返事した時刻、窓口が答えた時刻、ユーザーが読んだ時刻 |

本文の節には決まった名前がある。

- `## あなたの番`: ユーザーに何をしてほしいか（窓口が書く）
- `## 窓口の返事`: 窓口の答え。`### MM/DD HH:MM` の小見出しの下に Markdown で積む
- `## あなたの番への返事`: ユーザーの返事。`- MM/DD HH:MM: 本文` の 1 行ずつで積む
- `## メモ`・`## 資料` など

本文の Markdown は、正規の形（`gtd.py lint` の形）で書く。

### 4.3 リストの決まり

- プロジェクトのステップは、`done`・`next`・`waiting`・`planned` のどれかにする。`next` のステップが無くなったら、並びで最初の `planned` を `next` にする（`gtd.py` が行う）。
- プロジェクトの次のステップは、「次の行動」の箱にも出る（決まり）。
- 連絡待ちは、`watch` の PR がすべて閉じたら、次の行動に戻る（`gtd.py sweep`）。
- `done` の項目は、ふだんの箱には出さない。

### 4.4 読み書きの決まり

- 読むのは `gtd.py json` の出力だけ。形が変わったら合わせる（決まり）。
- 書くのは、すべて `gtd.py` のコマンドを通す。ファイルを直接書き換えない（決まり）。
  - lazygtd は `--by user` を付ける。エージェントは `--by agent:<名前>` を付ける。
  - `move`・`done` など、読んだときの hash を確かめるコマンドには `--hash` を付ける。
- `gtd.py` の終了コードは、次のように扱う（決まり）。

  | 終了コード | 意味 | lazygtd の動き |
  | --- | --- | --- |
  | 0 | 成功 | 読み直す |
  | 1 | 見つからない、など | 最下行で知らせる |
  | 2 | 形の誤り | 最下行で知らせる |
  | 3 | ぶつかり（ほかの人が先に直した） | 読み直してから、最下行で知らせる |

- 人の変更の記録（`gtd.py record`）は、lazygtd では動かさない。人の書き込みは、最後の変更から 10 分静かになったら、まとめてコミットされる（決まり）。lazygtd だけで暮らすなら、record を誰が動かすかを決める必要がある（未定）。
- ほかの人やエージェントが書き換えたら、すぐ画面に出す。`items/` と `.log/` の変化を見て、少しまとめてから読み直す（決まり）。

## 5. 画面

### 5.1 形（lazygit に寄せる）

- 左の列に、枠で囲んだ箱を縦に積む。右に、選んだ項目の詳細を出す大きな箱を置く（決まり）。
- 最下行に、いまの箱で使えるキーを出す（決まり）。
- 箱の大きさは、いつも同じにする。操作する箱を移っても、ほかの箱は縮まない。中身が多ければ、箱の中をスクロールする（決まり。lazygit の既定と同じ）。
- 枠の上の辺に、箱の名前と件数を出す（例: `[2] inbox (3)`）。番号の代わりにキーを出してもよい（向き）。
- 操作中の箱は、枠の色を変える。選んだ行は、背景を反転する（決まり）。
- メニュー、確かめ、入力は、画面の中ほどに出す小さな窓（ポップアップ）にする（向き）。
- 1 項目を 1 行にする。印（窓口の返事・あなたの番の理由・agent・締め切り）は題の前に置き、長い題が切れても印が見えるようにする（向き）。

### 5.2 色

ユーザーの端末の色（TokyoNight Storm）に合わせる（決まり）。lazygit の既定のテーマが使う色の番号を、次の値に当てる。

| 役目 | 色 |
| --- | --- |
| 背景 | `#24283b` |
| 文字 | `#c0caf5` |
| 操作中の枠 | 緑 `#9ece6a`（太字） |
| ほかの枠 | 文字の色 |
| 選んだ行 | 文字と背景を反転 |
| ほかの箱で選んでいた行 | `#364a82` |
| 最下行のキー | 青 `#7aa2f7` |
| 絞り込み | 水色 `#7dcfff` |
| 窓口の問い・承認 | 黄 `#e0af68` |
| 窓口の返事（まだ読んでいない） | 青系。問いとは色を分ける |
| 薄い文字 | `#a9b1d6`。`#4e5575` は本文に使わない |

コントラストの弱い色と、小さく見える文字は使わない（決まり）。

### 5.3 箱

| 箱 | 中身 |
| --- | --- |
| あなたの番 | ユーザーが今動くべきもの（5.4） |
| 窓口 | まだ読んでいない窓口の返事がある項目と、窓口の答えを待っている項目 |
| inbox | まだ振り分けていないもの |
| 次の行動 | `list: next`。プロジェクトの次のステップも出す |
| プロジェクト | `list: project`。詳細でステップを順に出し、どれが次かを示す |
| 連絡待ち | `list: waiting`。誰を待っているか、いつ確かめるかを出す |
| いつか | `list: someday` |
| 資料 | `list: reference` |

### 5.4 あなたの番

次のどれかに当たる項目を出し、理由も印で出す。

- worker の作業が終わり、ユーザーに戻された（`next`・`actor: me`・`worker` あり。handback）
- 連絡待ちの確かめる日が来た（`follow_up` が今日まで）
- 締め切りが来た（`due` が今日まで）
- 窓口や worker の問いがある（6 章。いまは lazygtd に無い）

worker の作業が終わってユーザーのレビューを待つときは、窓口がそれを `actor: me` の次の行動にする。本文には、レビューする資料のリンク、決めること、確かめる手順を書く（決まり）。

`actor: me` で worker の無い次の行動も「あなたの番」に出すかは、決めていない（未定）。

### 5.5 詳細

- 本文の Markdown を、端末で読める形で描く。見出し、表、リスト、コード、リンク（URL を出す）を扱う（決まり）。
- 窓口の返事とユーザーの返事は、時系列で会話のように並べる（決まり）。
- 詳細の下に返事の欄を置く（決まり。7 章）。
- 日本語の幅（全角）で、表の列がずれないようにする（向き。いまは少しずれる）。

## 6. 操作

### 6.1 キーの考え方

- lazygit の既定のキーと振る舞いを正にして、GTD の操作を当てはめる。前に決めたブラウザのデスクのキーは守らなくてよい（決まり）。
- 対応表（lazygit のキー → lazygtd の操作）を README か別の文書に置く（向き）。
- 数字のキーは、ユーザーのキーボードではレイヤーキーと同時に押す必要がある。数字で箱へ飛ぶ lazygit の決まりは残しつつ、`h`/`l`・`Tab`/`Shift+Tab` でも箱を移れるようにする（決まり）。
- 日本語の変換中のキー（変換を決める Enter など）では、操作も送信もしない（決まり）。

### 6.2 操作の一覧

キーの割り当ては「向き」。操作そのものは「決まり」。

| 操作 | キーの案 | 中身 |
| --- | --- | --- |
| 箱を移る | `h`/`l`、`Tab`/`Shift+Tab`、数字 | lazygit と同じ |
| 行を上下 | `j`/`k` | 箱の中で動く。端から反対の端へ回る |
| 中に入る、戻る | `Enter`、`Esc` | `Enter` で返事の欄へ入る |
| 作る | `c` | 小さな窓で題と本文を書き、`gtd.py add --list inbox --by user` で入れる（7 章）。ほかの箱で `c` を押したときに、その箱のリストに作るかは未定 |
| 移す | メニュー | 移す先（inbox・次の行動・プロジェクトのステップ・連絡待ち・いつか・資料・カレンダーに入れる）を、小さな窓のメニューで選ぶ |
| 完了 | `x` などの案 | `gtd.py done`。lazygit で `x` はメニューなので、寄せるなら選び直す |
| エディタで開く | 1 つのキー | 項目のファイルを開く |
| 成果物を開く | 1 つのキー | `items/<id>/` を開く |
| 返事を書く | `Enter` | 7 章 |
| 絞り込み | `/` | いまの箱の中を絞り込む。入力欄は最下行 |
| キーの一覧 | `?` | 小さな窓で出す |
| 詳細をめくる | `Ctrl+D`/`Ctrl+U` など | 長い本文を読む |
| 読み直す | `Ctrl+R` など | |
| 終わる | `q` | lazygit と同じ。`Ctrl+C` でも終わる |

まだ無いが要る操作（向き）。

- プロジェクトのステップを足す、並べ替える、外す（`gtd.py step`）
- 締め切り（`due`）と、連絡待ちの欄（`who`・`follow_up`・`then`・`watch`）を入れる、直す
- `actor` を `me` と `agent` のあいだで切り替える

### 6.3 書く欄のキー

すべての書く欄で、次のとおりにそろえる（決まり）。ユーザーは、どの画面でも「`Ctrl+J` で改行、`Enter` で送信」にそろえたい。

| キー | 何行も書ける欄 | 1 行の欄（絞り込みなど） |
| --- | --- | --- |
| `Enter` | 送る | 決める |
| `Ctrl+J` | 改行 | 何もしない（改行のつもりで押して送らないように） |
| `Shift+Enter` | 改行 | 何もしない |
| `Esc` | 欄から抜ける | 欄から抜ける |

- 空の欄では送らない。
- 書いているあいだは、ほかの操作のキーを受け付けない。

### 6.4 エディタで開く

- Orca のターミナルの中（環境変数 `ORCA_PANE_KEY` がある）なら、`orca file open <path> --focus` で Orca のエディタに開く（決まり）。
- それ以外では、`$EDITOR`（無ければ nvim）で開く。画面を明け渡し、閉じたら戻る（決まり）。
- `LAZYGTD_EDITOR` で、どちらにするかを決められる（決まり）。
- 開けるのは `items/<id>.md` と `items/<id>/` の下だけにする。シンボリックリンクの先も確かめる（決まり）。

## 7. 窓口とのやり取り

### 7.1 頼む

- 新しく頼みたいことは、lazygtd の中で `c` を押して書く。窓口のターミナルは開かない（向き）。
- `c` の窓は、lazygit のコミットの窓と同じく、1 行目を題、`Ctrl+J` のあとを本文にする（向き）。
- 書いたものは inbox に入る。inbox に人が足した項目は、窓口に知らせが届く（決まり。知らせるのは lazygtd ではない。7.4）。
- inbox に入れたものを全部頼みごとにするか、頼みごとの印を付けるかは決めていない（未定）。案は次のとおり。
  - inbox に入れたものは、全部窓口が拾う。窓口が、頼みごとかメモかを見分け、迷ったら項目の上で聞く
  - `c` は inbox に入れるだけにし、窓口に頼む操作を別のキーにする
  - 項目に「窓口に頼む」の印を付ける

### 7.2 窓口の答えを読む

- 窓口は、答えを項目の「窓口の返事」に書く（`gtd.py reply`）。`answered` が `read` より新しければ、まだ読んでいない（決まり）。
- まだ読んでいない返事のある項目は、「窓口」の箱に出し、印を付ける（決まり）。
- 項目を 0.8 秒ほど表示したら、読んだ印を付ける（`gtd.py read`）。`j`/`k` で通り過ぎただけでは付けない（決まり）。
- 新しい返事が来たら、目立たせて知らせる（向き。端末の題名や最下行など）。

### 7.3 答える

- 詳細の下の返事の欄で書き、`Enter` で送る。`gtd.py say --by user` で、本文の「あなたの番への返事」に 1 行足し、`asked` に時刻を入れる（決まり）。
- `asked` が `answered` より新しければ、窓口の答えを待っている。「窓口」の箱に出す（決まり）。
- `say` は改行を空白にまとめる。何行もの返事を残すかは決めていない（未定）。

### 7.4 窓口への知らせ（lazygtd の外）

窓口に知らせるのは、lazygtd ではなく、別の常駐の仕組み（いまは Orca の Hub (local) プラグイン）が行う。lazygtd は `gtd.py` で書くだけで、知らせのことを知らなくてよい（決まり）。

- 知らせの元は `.log/changes.jsonl`。次のときに、窓口のターミナルに 1 行で知らせる。
  - ユーザーの返事（`say`、`by: user`）
  - inbox への追加（`add`、`list: inbox`、`by: user`）
  - `actor: agent` で worker の無い項目が、次の行動に入った（30 秒待ってから）
- 知らせには項目の id だけを入れ、題や本文は入れない。題の文が、窓口への指示として読まれないようにするため。
- 同じ項目は 1 回だけ知らせる。届かないときは 30 秒ごとに送り直す。
- その仕組みが動いていない所（私用の環境など）では、知らせは届かない。lazygtd は、知らせが無くても単体で使える（決まり）。私用の環境で窓口とつなぐなら、同じ役目を別に作る（未定）。

### 7.5 窓口の決まり（lazygtd が前提にすること）

lazygtd の外の決まりだが、画面の作りに関わる。

- 頼まれた話題は、窓口が項目にするか、もとからある項目に結ぶ。答えは項目に書き、ターミナルには id と題の 1 行だけを返す。
- `actor: agent` の項目が次の行動に入ったら、窓口がすぐ worker を起こして結ぶ。
- 方針の合意が要るものは、`actor: me` で次の行動に入れる。合意できたら `agent` にして worker を起こす。合意が要るかの目安は、外に出る操作がある、設計の選択がある、好みで答えが変わる、完了の条件が読み取れない、費用や権限やほかの人の時間がかかる、のどれか。
- 返事は承認ではない。外に出す操作は、窓口が別に承認を聞く。

## 8. 問い・承認・許可の確認（これから）

いまはブラウザのデスクにしか無い。lazygtd にも置く（向き）。

### 8.1 種類

| 種類 | 中身 |
| --- | --- |
| 窓口の問い | 選択肢（推奨の印つき）と本文（Markdown）。自由に書いて答えることもできる |
| 承認の問い | 外に出す操作をしてよいか。選択肢つき |
| 許可の確認 | エージェントがコマンドなどを動かしてよいか。許可・拒否・理由を書く・ターミナルで決める。待てる時間が短い（いまは 180 秒） |
| worker の問い | worker が判断を求める問い |

### 8.2 見せ方と答え方

- 「あなたの番」のいちばん上に置き、ほかの印より目立たせる（黄）。許可の確認には残り時間を出す（向き）。
- 待っている数を、端末の題名や最下行にも出す（向き）。
- 選択肢は 1 つのキーで答える。デスクでは `Shift+Q`〜`Shift+R`（キーの位置で見て、Caps Lock で取り違えない）。lazygtd のキーは、lazygit に寄せて選び直してよい（向き）。
- 許可の確認のキーは固定し、押し間違えても別の答えにならないようにする（決まり）。
- 新しい問いが来ても、選んでいる行と、書いている途中の入力は動かさない（決まり）。

### 8.3 作りの方針

- 答えを渡す処理と承認の記録は、いまは Hub (local) の中にある。lazygtd から直接は書けない。
- 「どの画面からも同じ口」の考えで、答えを渡すコマンド（例: `asks.py answer <id> <番号>`）を Hub とスキルの側に作り、ブラウザのデスクと lazygtd の両方から呼ぶ形を勧める（向き）。
- 問いのファイル（`state/asks/<id>.json`）は読める。答えの正しさは、窓口が `asks.py verify` で確かめる。
- 情報の扱いの区分が高い問いは出さない、という守りはデスクと同じにする（決まり）。

### 8.4 worker の様子

- worker が今どこまで進んだか（タスクの数など）と、worker の画面への切り替えは、Hub の側に読める口ができてから（未定）。

## 9. 速さと安定

- 速さの目安: 起動から最初の画面まで 100 ms 以内、キーから描き直しまで 20 ms 以内（向き。いまは 75 ms と 11 ms）。
- ネットワークもトークンも使わない。頼るのは `gtd.py` と端末だけ。Orca に頼るのは、エディタで開くときだけにする（決まり）。
- 書き込みは画面のループの外で動かす。同じ項目への二重の書き込みは止める（決まり）。
- `gtd.py json` に読めない項目（`broken`）があれば、どのファイルの何が読めないかを出す（向き）。

## 10. 作りと試し

- Go と jesseduffield/gocui（lazygit が使う fork）で作る。本文の描画は glamour（決まり）。
- 画面の無い状態（箱・行・選択・キーの判断）は、gocui に頼らない形にして、テストしやすくする（決まり）。
- 画面のテストは、gocui の headless で、本物の `gtd.py` をデモのフォルダに対して動かす（決まり）。
- デモの項目（`scripts/demo-home.sh`）は、ふだんに近い量と種類にする。箱ごとに数件〜十数件を置く。プロジェクトとステップ、連絡待ち、締め切りが近いものと過ぎたもの、`agent` と `me`、まだ読んでいない返事と答え待ち、長い題、長い本文（表・リンク・コード）を入れる。中身は作りものにし、実在の名前や URL を入れない（決まり）。
- lazygit のコードを写すときは、lazygit の著作権とライセンスの表示を付ける（`NOTICE.md`）（決まり）。
