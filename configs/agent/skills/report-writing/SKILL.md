# 報告資料の書き方

報告を受ける側が、短い時間で状況をつかみ、安心して判断できる資料にする。

## 組み立て（空雨傘）

次の 3 つの見出しで、この順に書く。

1. **現状**（空）: 事実だけを書く。進んだこと、止まっていること、数字
2. **見立て**（雨）: 現状から何が言えるか。予定どおりか、どこに危うさがあるか
3. **ネクストアクション**（傘）: 見立てを受けて、誰が・いつまでに・何をするか

3 つ目の見出しは「ネクストアクション」にする。「次の手」「今後の予定」などに言い換えない。

## ネガティブなこと

- 遅れや問題は隠さずに書く。隠すと、あとで分かったときに信頼を失う
- 書くときは、対策か、決める日と組にする。報告を受ける側を不安にさせないため
  - 例: 「検証環境の準備が 3 日遅れています。11/10(火) までに代わりの環境で進めるか決めます」
- 上長に頼みたいこと（判断、調整、承認）は、本当にあるときだけ書く。無いのに「特になし」の欄を作ったり、形だけの依頼を書いたりしない

## 文体

- 丁寧語（です・ます）で書く
- 人名には「さん」を付ける（例: 「山田さん」）
- 表の中の短い名詞句（到達点、タスク名、状態など）は、名詞の形のままでよい。文にするのは表の外の説明と、表の中でも文になっている欄

## 書かないこと

- 相手が別の資料ですでに知っていること（目指す状態、進め方、体制など）は繰り返さない。その資料へのリンクで済ませる
- 報告に要らない作業の細部。相手の判断に関わる粒度までにする

## リンクと日付

- チケット ID と PR 番号はリンクにする。表示名は ID そのもの（例: `[ABC-123](https://...)`、`[#123](https://...)`）
- 日付には曜日を付ける（例: `11/4(水)`）。リンクと曜日は、外部への送信では `external-post-guard.py` が確かめて止める。資料でも同じにする

## 例（架空）

```markdown
## 現状

* 検索機能の改善は、3 つの到達点のうち 2 つが完了しました（[ABC-120](https://example.com/ABC-120)、[ABC-121](https://example.com/ABC-121)）
* 残りの到達点は、検証環境の準備が 3 日遅れています

## 見立て

* 全体の完了は 11/20(金) の予定どおりと見ています。遅れは検証の順番の入れ替えで吸収できます

## ネクストアクション

* 11/10(火) までに、代わりの環境で検証を進めるか決めます（佐藤さん）
* 決まり次第、残りの到達点の検証を始めます
```

## Google Docs に貼るとき

Google Docs の「Markdown から貼り付け」は、`- ` の箇条書きの入れ子を正しく読めないことがある。貼り先が Google Docs なら、資料を Markdown のファイルに書いてから次のコマンドでコピーし、ユーザーに「Markdown から貼り付け」で貼ってもらう。

```sh
python3 ~/.claude/skills/report-writing/scripts/md_to_gdocs.py <ファイル>
```

- 箇条書きの記号 `- ` を `* ` に直す（入れ子も）。コードブロックの中、表、水平線は変えない
- macOS では pbcopy でクリップボードに入れる。pbcopy が無い環境や `--stdout` を付けたときは標準出力に出す
- ファイルを省くか `-` にすると標準入力を読む
